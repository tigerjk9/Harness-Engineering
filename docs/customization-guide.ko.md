# 하네스 구축 가이드 — 암묵지를 명시지로 변환하기

> 이 가이드는 EduHarness 템플릿을 **당신의 프로젝트에 맞게 진화시키는 방법**을 설명합니다.
> clone 직후 이 파일을 먼저 읽으세요.

---

## 실전 하네스 구축 파이프라인 6단계 {#파이프라인}

> 새 교육 프로젝트를 시작할 때 이 순서를 따르세요.
> EduHarness는 이 6단계를 모두 파일과 스킬로 구현해 놓았습니다.

```
┌──────────────────────────────────────────────────────────────────┐
│              실전 하네스 구축 파이프라인                           │
└──────────────────────────────────────────────────────────────────┘

1단계                2단계                3단계
아이디에이션       헌법 제정            자율 검증 및 정렬
& 아키텍처
[빈 폴더 → 구조]  [CLAUDE.md 작성]    [AI가 문서 모순 교정]
      │                  │                    │
      ▼                  ▼                    ▼
architecture.md      CLAUDE.md           verify 스킬
progress.md          AGENTS.md           (하네스 검증)

4단계                5단계                6단계
Git 체크포인트      암묵지 명시화        MBO 실행 루프
[영구 기억 장치]    [당연한 것 → 규약]  [AI 자율 반복]
      │                  │                    │
      ▼                  ▼                    ▼
.husky/pre-commit   이 가이드 전체       execution-loop
git commit 관습     CLAUDE.md 규칙 추가  스킬 + AGENTS.md
```

### 단계별 EduHarness 파일 매핑

| 단계 | 핵심 행동 | 사용할 파일/스킬 |
|------|-----------|----------------|
| **1. 아이디에이션 & 아키텍처** | 폴더 구조와 기술 스택을 AI와 합의 | `architecture.md` 채우기 |
| **2. 헌법 제정** | 타협 불가 원칙(보안·교육 규칙·코딩 스타일) 설정 | `CLAUDE.md` `[대괄호]` 채우기 |
| **3. 자율 검증 및 정렬** | AI가 문서 간 논리적 모순 스스로 교정 | `[verify 스킬 사용]` 실행 |
| **4. Git 체크포인트** | 하네스 초기 버전을 영구 기억으로 저장 | `.husky/pre-commit` + 첫 `git commit` |
| **5. 암묵지 명시화** | 머릿속 "당연한" 가정 → CLAUDE.md 규칙 추가 | 이 가이드의 2~5단계 반복 |
| **6. MBO 실행 루프** | 검증 기준 충족까지 AI가 코드 작성·수정 자동 반복 | `[execution-loop 스킬 사용]` |

### 파이프라인 실행 예시

```
# 1단계: AI와 함께 구조 합의
"빈 Next.js 프로젝트에서 교육 퀴즈 앱을 만들려고 해.
 architecture.md를 채우기 위해 기술 스택과 폴더 구조를 제안해줘."

# 2단계: 헌법 제정
"CLAUDE.md의 [대괄호]를 채워줘.
 우리 앱은 초등학생 대상이고, 형성평가 중심이야."

# 3단계: 자율 검증
"[verify 스킬 사용] CLAUDE.md와 architecture.md 간 논리적 모순이 있는지 검증해줘."

# 4단계: Git 체크포인트
git add CLAUDE.md architecture.md progress.md
git commit -m "harness: 초기 헌법 및 아키텍처 설정"

# 5단계: 암묵지 명시화 (개발하면서 계속)
"방금 퀴즈 컴포넌트를 만들다가 알게 됐어.
 재시도 버튼은 형성평가에서만 보여야 해. CLAUDE.md에 이 규칙 추가해줘."

# 6단계: MBO 실행 루프
"[execution-loop 스킬 사용] 학생 퀴즈 응시 기능을 구현해줘."
```

## 왜 이 과정이 중요한가?

하네스 엔지니어링의 핵심은 **암묵지(Tacit Knowledge)를 명시지(Explicit Knowledge)로 변환**하는 것입니다.

당신의 머릿속에는 수많은 "당연한 것들"이 있습니다:
- "우리 앱은 초등학생용이니까 어려운 용어는 쓰면 안 되지"
- "DB 스키마는 팀장 승인 없이 변경하면 안 되지"
- "퀴즈는 재시도 무제한이어야 하지"

이것들을 AI는 모릅니다. 당신이 명시하지 않으면 AI는 일반적인 채점 시스템을 만들고,
어려운 용어를 쓰고, DB를 마음대로 바꿉니다.

**하네스는 그 "당연한 것들"을 코드로 만드는 작업입니다.**

## 1단계: 하네스의 2계층 구조 이해

```
레포지토리 하네스 (건드리지 마세요)
├── .claude/skills/       # 교육 도메인 공통 스킬
├── .claude/settings.json # 자동화 훅
└── .husky/pre-commit     # 자동 검증

애플리케이션 하네스 (여기를 채우세요)
├── CLAUDE.md             # ← 이 프로젝트의 헌법
├── AGENTS.md             # ← 에이전트 역할 (필요에 따라 수정)
├── architecture.md       # ← 시스템 구조 정의
└── progress.md           # ← 진행 상태 추적
```

**레포지토리 하네스**는 공통 원칙입니다. 교육 도메인 규칙(형성/총괄 평가, WCAG 등)이 내장되어 있으므로 처음에는 수정하지 마세요.

**애플리케이션 하네스**는 당신의 프로젝트 전용입니다. 이 4개 파일의 `[대괄호]`를 채우는 것이 시작입니다.

---

## 2단계: CLAUDE.md — 헌법 작성 (가장 중요)

CLAUDE.md는 AI 에이전트가 세션 시작 시 자동으로 읽는 **헌법**입니다.

### 채워야 할 항목

```markdown
## 프로젝트 목적
[YOUR_PROJECT_NAME] → 예: "EduQuiz Pro"
대상 사용자: [예: 초등학교 3-6학년 교사]
핵심 기능: [예: 퀴즈 생성, 학생 진도 추적]
```

**작성 팁 — AI와 대화하며 채우기:**
```
"우리 교육 앱의 핵심 특징 5가지를 질문해줘.
내 답변을 바탕으로 CLAUDE.md의 프로젝트 목적 섹션을 채워줘."
```

### 주요 명령어 채우기

```markdown
## 주요 명령어
npm run dev      # ← 실제 명령어로 교체
npm test         # ← 실제 명령어로 교체
npm run lint     # ← 실제 명령어로 교체
```

### 너무 길면 AI가 안 읽는다

CLAUDE.md는 **800줄 이하**로 유지하세요.
핵심만 남기고 나머지는 `docs/` 폴더로 분리합니다.

---

## 3단계: architecture.md — 작업 구조 정의

시스템 구조를 문서화합니다. AI가 코드를 어디에 어떻게 배치해야 하는지 알게 됩니다.

### 최소한 채워야 할 것

```markdown
| 프로젝트명 | EduQuiz Pro |
| 목적 | 교사가 퀴즈를 만들고 학생 진도를 추적하는 웹앱 |
| 기술 스택 | Next.js 14, TypeScript, PostgreSQL, Tailwind |
| 배포 환경 | Vercel (프론트) + Railway (DB) |
```

**디렉토리 구조는 실제 프로젝트 구조와 일치해야** AI가 올바른 위치에 파일을 만듭니다.

---

## 4단계: AI와 논리적 일관성 검토

문서를 다 채웠다면 AI에게 검토를 요청하세요:

```
"시니어 개발자 관점에서 CLAUDE.md와 architecture.md를 읽고,
서로 모순되는 내용이 있는지 확인해줘.
모순이 있으면 어느 쪽을 수정해야 하는지 알려줘."
```

```
"보안 전문가 관점에서 CLAUDE.md의 규칙들을 0-10점으로 평가해줘.
모호한 표현이 있으면 구체적인 수치나 코드로 바꿔줘."
```

---

## 5단계: Git으로 하네스 버전 관리

하네스의 진짜 가치는 **시간이 흐를수록 고도화되는 것**입니다.

```bash
# 하네스 개선 시마다 커밋
git add CLAUDE.md architecture.md
git commit -m "harness: 퀴즈 형성평가 규칙 구체화"

# 프로젝트와 분리된 하네스 브랜치 (선택)
git checkout -b harness/v2
```

매 프로젝트마다 하네스가 진화하면, 다음 프로젝트는 더 나은 출발점에서 시작합니다.

## 위임형 상사 모델

하네스를 잘 구축했다면, AI 사용 방식도 바꿔야 합니다.

### 3가지 상사 유형

**지시형 상사 ❌** — AI의 창의적 해결 공간을 제한
```
"로그인 버튼을 파란색(#3B82F6)으로 만들고,
 텍스트는 16px 굵게, 패딩은 12px 16px로 해줘."
```

**방임형 상사 ❌** — 기대치 미달 결과
```
"로그인 페이지 만들어줘."
```

**위임형 상사 ✅** — 목표와 기준을 제시하고 방법은 AI에게
```
"[Coder] 학생 로그인 페이지를 만들어줘.
 - 대상: 초등학생 (단순하고 큰 UI)
 - WCAG 2.1 AA 접근성 준수
 - 만 14세 미만은 보호자 동의 플로우 연결 (CLAUDE.md 규칙 5 참조)
 - 완료 후 progress.md 업데이트해줘."
```

### 위임이 잘 되는 조건

1. **명확한 완료 기준**: "WCAG 2.1 AA 준수" 처럼 측정 가능한 기준 제시
2. **참조 문서 지정**: "education-principles.md 참조" 처럼 어디를 읽어야 하는지 알려주기
3. **후속 행동 명시**: "완료 후 progress.md 업데이트" 처럼 마무리 행동까지 지정

## 자주 하는 실수

### 실수 1: 하네스를 한 번 쓰고 끝냄

하네스는 **살아있는 문서**입니다. 프로젝트를 진행하면서:
- 새로운 금지 행동 발견 → CLAUDE.md에 추가
- 아키텍처 결정 → architecture.md에 기록
- 효과적인 프롬프트 패턴 → AGENTS.md 예시에 추가

### 실수 2: 너무 많은 규칙

CLAUDE.md에 규칙이 50개가 넘으면 AI가 다 읽지 않습니다.
핵심 10-20개만 남기고 나머지는 `docs/`로 분리하세요.

### 실수 3: 모호한 규칙

```
❌ "코드를 깔끔하게 짜라"
✅ "함수는 50줄 이하, 파일은 800줄 이하로 유지하라"

❌ "보안에 신경 써라"
✅ "정답 데이터는 API 응답에 절대 포함하지 말 것 (assessment-integrity 규칙)"
```

### 실수 4: 역할 없이 사용

역할 없이: `"퀴즈 만들어줘"` → AI가 계획·구현·검토를 동시에 하다가 품질 저하

역할 있이: `[Planner] 계획 수립 → [Coder] 구현 → [Pedagogy Reviewer] 교육학적 검토`
